# 15 · OMP 分阶段、多 Agent 工作流

此文档定义本项目编排策略，不是 OMP 配置文件，也不是强制权限沙箱。OMP 的真实参数以安装版本和当前会话工具 schema 为准。已核对来源见 [OMP 来源](../references/OMP-SOURCES.md)。

## 工作闭环

主 Agent 读取现状 → 明确本阶段契约 → 小任务单 → worker 实现/测试 → 主 Agent 集成实测 → 新上下文 reviewer → 修复与复核 → 主 Agent 写 verified → 停止。

沿用 00–19 阶段编号及 164 条产品测试要求；新增的 OMP 接入检查放在独立 checklists/omp-readiness.csv，不改号、不冲掉已有进度。只改变开发方式，不改变网关运行时架构。

## 角色与权限

| 身份 | 职责 | 允许写入 | 禁止事项 |
|---|---|---|---|
| 主 Agent | 规划、接口、分派、集成、验收 | 当前批准范围、总状态、阶段证据 | 无界实现、未经批准换主模型、跳门禁 |
| urbino-scout | 精准读代码/官方依据 | 无 | 写代码、运行 shell、派生 Agent |
| urbino-implementer | 按契约编写实现与必要单测 | 任务显式分配文件 | 改验收规则、总状态、未授权生产配置 |
| urbino-tester | 边界/并发/故障测试与复现 | 显式分配测试文件及自己的证据 | 删断言、改生产默认放行、改总状态 |
| urbino-reviewer | 独立读取最终代码/证据 | 无 | 自己修复自己的审查对象、宣称实跑未跑测试 |
| urbino-security | 安全/账本专项只读审查 | 无 | 外网攻击/扫描、读取真实秘密、自行放行 |

发行的 Agent 定义故意不硬编码 model。setup 在核实真实配置与角色后，仅给这五份项目 Agent 文件绑定真实模型或确认支持的别名，并记录实际解析结果。未绑定/未验证不得派任务，避免默默继承昂贵默认模型。只读工具列表只减少写入口，不能阻止读取工具访问不应访问的数据；仍须路径与秘密约束。

## 任务合同

每个任务使用 templates/OMP_TASK.md：一个可验收目标、明确非目标、固定公共接口、文件所有权、依赖、测试编号、实际可用命令、产物路径及停止条件。不得下发“做完所有鉴权”之类无边界任务。一次任务以可独立验证的一个切片为限，模型无进展时缩小范围而非盲目增加上下文。

共享工作区：主 Agent 在 progress/plans/NN.md 维护文件所有权。同一 migration 目录、go.mod/go.sum、生成的 sqlc/OpenAPI 文件、公共接口和路由装配由一个任务或主 Agent 串行处理；生成产物不得手工修补。

隔离工作区：先验证当前 OMP 是否自动应用补丁、生成提交，以及未跟踪文件/初始无 commit 的仓库如何处理。未获 Git 提交授权时，不启用会隐式提交的隔离模式。不能假定“worktree”天然防冲突或自动隔离环境变量/网络。主 Agent 检查实际返回补丁和最终文件，冲突须人工审查式解决，禁止 reset --hard。没有安全隔离就用单写入者串行，而不是为了隔离让用户启用虚拟化。

## 小模型质量控制

主 Agent先给接口、错误分类、约束和金样例；worker负责落实，不单独决定 OAuth 轮换、请求重试、金额精度或越权边界。测试角色在契约稳定后写失败路径与并发测试，不机械复述实现者代码。高风险阶段增加独立 security reviewer。

初始并行 2，上限 4，总子 Agent深度 1；这些是项目策略，不宣称修改了 OMP 全局配置。默认不打开 advisor/prewalk，也不改用户原来的 compaction、Base URL、Key 或其他模型配置。不用自动模式跳过审批。

同一缺陷最多两轮无进展后主 Agent检查根因；需要更强模型时只在已核验的候选中切换子任务，不改当前主会话。不宣称固定节省比例；有实际 usage 才统计。

## 工具与异步结果

OMP task 的参数会随 batch/isolation/effort 设置变化。使用正在暴露的 schema：批量有 context/tasks，单任务有 agent/task；仅有 isolated 字段时才能传它，不使用猜测的 model/isolation/cwd/output 字段。具体字段演变参见 OMP 源码；本段不是要复制固定 payload。

子 Agent通过当前实际支持的 yield 输出。要求字段见 templates/OMP_WORKER_REPORT.md。不假定某一版本接受 JSON Schema 或 JTD 的任意变体；发行 Agent 的基础 output 使用已核对的 JTD 子集，setup 必须验证解析。task 的返回 ID、queued、timeout、部分输出不是 completed。

主 Agent等待全部任务到终态，失败任务记录已产生的变更；恢复会话先核查活跃任务及文件差异，不能重复发同一写任务。临时 agent:// 路径仅作运行中引用；持久证据是仓库内脱敏文件。

## 独立验收

reviewer 不参与实现，使用新上下文，检查原规格、最终差异、测试代码及原始输出。只读 reviewer 不运行测试；主 Agent或 tester负责实跑，reviewer明确“观察证据”与“亲自执行”的区别。

主 Agent是状态文件的唯一写入者。新代码 revision 使受影响的旧审查失效，需要重跑并重新确认；无关历史证据保留，不重置全项目。OMP todo 与会话记忆不能覆盖仓库的进度真相。

## 上线边界

开发 harness 的模型调用与网关产品 live tests 是两件事。前者复用用户已授权开发中转，后者需 host/model/预算/凭据/环境的显式批准。提示词不会自动部署、开收费调用、降低鉴权或读取生产数据。
