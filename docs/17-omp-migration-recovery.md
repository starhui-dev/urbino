# 17 · 迁移与恢复

## 新工程

将发行包解压后的目录内容（包含隐藏的 .omp/）放到新仓库根目录；无需安装新的付费插件。进入根目录启动现有 omp，再用 /urbino-start。该入口先 setup，仅在 OMP 路由与烟测通过后实现 00 阶段；之后停止等待复核。

## 已有工程：不覆盖解压

先把本包解压到工作仓库之外的独立目录。在当前工作仓库的 OMP 会话中直接要求阅读该目录 prompts/MIGRATE_TO_OMP.md，按实际文件差异合并。新版的初始 progress/state.json、checklists/test-matrix.csv 执行状态、模板空证据不是已有工程的实际进度，绝不能覆盖。

tools/migration_plan.py 默认只生成计划、不改任何目标文件，可识别新增、相同、待合并和必须保留的运行数据。报告中只有路径/摘要，不含文件内容或秘密。计划不会自动复制、删除或重命名源代码、历史证据、真实配置、数据库对象。

合并顺序：备份与基线 → AGENTS/主控规则 → 项目名称契约 → OMP 项目文件 → 阶段追加编排与工具 → 对照已有 progress → setup → 复核受影响阶段。新名称只有 Urbino，不能保留中文产品名或附加产品后缀；但不得把外部协议名、URL 或历史数据强制重写。

旧 Agent 配置、其他开发工具配置和秘密不属于自动删除范围。失效的命名提示词可保留为转向新迁移提示词的入口，防止旧链接失效；不能同时存在互相矛盾的活动规则。

## 进度处理

阶段 ID、状态、历史报告和既有证据保留；只更新实际需要的 harness 元数据。已有 verified 不能全部重置，也不能不检查就全保留：按影响范围记录 stale_reason 并重新验收。若增加字段，兼容旧证据，不根据缺字段伪造旧模型/会话信息。

状态文件采用主 Agent 单写、先写临时文件再原子替换；不要让多个 task 同时落阶段结论。每次变更记录前一状态、基线 revision 与原因。

## 中断与上下文压缩

先读仓库 state、最新报告/交接、Git diff 及 OMP 实际任务状态。task 仍活跃时先收集/终止，不重复发送写任务。上下文压缩前保存 templates/OMP_HANDOFF.md；命令输出保留在 evidence，不复制巨量日志到主会话。

测试失败回到修复任务，不运行 /reset 或删除 progress。已经运行到 implemented 则先独立 review，不在 /next 中直接重做。使用外部测试环境前重核环境名称、权限、host 与预算，不能沿用另一阶段的生产权限。
